# VibeKit Documentation Feature Spec

Version 1.0 · a component of the VibeKit Specification (§66)

## 1. Purpose

> **In plain terms.** VibeKit keeps a proper set of architecture documents for the software it builds — high level, low level, API reference, data model and an operations runbook — with real diagrams. They are generated from the same facts the code is checked against, so they cannot quietly go out of date. You put your company's document templates in a folder and the output comes back in your house style. If you do not have a template, VibeKit builds one from your website.

Architecture documentation fails for one reason: it is written once, by hand, and the code moves. Within a month the diagram is wrong, within a quarter nobody trusts it, and within a year it is deleted. Every attempt to fix this with process has failed because the process depends on a person remembering.

This feature removes the person. **Nothing is drawn by hand and nothing is written twice.** A diagram is a view of an architecture model; the model is generated from the same files that govern the build and is checked against the code on every merge. A document that disagrees with the code is a failing check, not a stale artefact somebody should get around to.

### Scope

In scope: the `docs/` folder, the architecture model, the template system, brand extraction, five generated documents, the update cadence and the drift checks that keep them honest.

Out of scope: anything about how the software itself is built, which is the VibeKit Specification. This document depends on that one and does not repeat it.

### What this is not

It is not a diagramming tool. There is no canvas, no dragging boxes, and no way to draw something the model does not contain — because a diagram that can disagree with the code is the problem this feature exists to solve. If a diagram is wrong, the fix is in the folder, and the diagram follows.

It is also not a wiki. Documents are outputs with a commit stamp, reproducible at any past tag. Prose that a human owns lives in clearly marked authored sections that are never overwritten.

## 2. Layout

`docs/` sits at the repo root, beside `vibekit/` rather than inside it. The folder is machine context; `docs/` is human output. That separation matters: `docs/` can be published, printed, emailed and handed to an auditor without exposing the working files, and a reader who opens the repo finds documentation where they expect it.

```
<repo>/
├── vibekit/                 the machine's context (VibeKit Specification, Part A)
└── docs/
    ├── brand.yml            YOURS · logo, colours, type, footer · the only file you need
    ├── assets/              YOURS · logo.svg · logo-mono.svg · favicon.png
    ├── model.dsl            GENERATED · Structurizr · the single source for every diagram
    ├── views.dsl            YOURS · which diagrams to render · optional
    ├── diagrams/            GENERATED · svg + png
    ├── hld.md               GENERATED at gates
    ├── lld.md               GENERATED at gates
    ├── api-reference.md     GENERATED from contract tests + OpenAPI
    ├── data-model.md        GENERATED · ERD + field reference
    └── runbook.md           half generated, half yours
```

One level, and one file you have to care about. `brand.yml` is the letterhead, which is what actually makes a document look like yours; the structure of each document is built into VibeKit.

Three things appear only if you ask for them: `templates/` when you want to take over a document's structure (below), `decisions/` when ADRs are switched on, and `.docs-state.json` for hashes and commit stamps, which is git-ignored.

### Ownership

The three kinds of file from the VibeKit Specification §3 apply unchanged:

| Path | Kind | Rule |
| --- | --- | --- |
| `brand.yml`, `assets/` | Authored | Written once by `--brand`, then yours forever |
| `views.dsl` | Authored | Optional. Present only if you want to change which diagrams exist |
| `templates/*.md` | Authored | Optional. Present only for documents whose structure you have taken over |
| `model.dsl`, `diagrams/**` | Generated | Rewritten when the architecture changes; carry the `generated by vibekit` header |
| `hld.md`, `lld.md`, `api-reference.md`, `data-model.md` | Generated | Rewritten at gates |
| `runbook.md` | Mixed | Sections marked authored are never overwritten |
| `decisions/**` | Generated | Only when `docs.adr` is on |
| `.docs-state.json` | State | Git-ignored, rebuilt on demand |

Editing a generated document is allowed and has a consequence: the `generated by vibekit` header disappears, VibeKit stops overwriting that file, and `vibekit check` reports it as detached with the date. That is a choice, not an error, but it is visible.

## 3. The architecture model

One Structurizr DSL file, generated from the folder, from which every diagram is rendered. Structurizr was chosen over hand-drawn diagrams and over per-diagram Mermaid because a single model cannot contradict itself across four levels, and because it exports to SVG, PNG, PlantUML and Mermaid when a viewer needs one.

### What generates each element

| Model element | Generated from |
| --- | --- |
| People and roles | `product/access.md` roles, `product/context.md` users |
| Software system | `product/context.md` |
| External systems | `## Dependencies` and trust boundaries in `workflow/architecture.md` |
| Containers | The deployables in `product/map.md`, and `system.md` in a multi-repo setup |
| Components | Layers and modules in `map.md`, reconciled against `bindings.json` for what is actually there |
| Relationships | Entity relations, API contracts from contract tests, integration direction |
| Deployment nodes | `delivery/environments.md`, only when delivery is enabled |
| Styles | `docs/brand.yml` |

The reconciliation against `bindings.json` is the part that matters. `map.md` says where code is supposed to go; `bindings.json` records where it actually went. A component that exists in the code but not in the intended structure appears in the model marked as unplanned, and is reported. Diagrams that only show the intention are the reason nobody trusts architecture documents.

```
# docs/model.dsl · generated by vibekit · do not edit · source: architecture
workspace "Teamly todo" {
  model {
    member    = person "Team member"  "Creates lists and tasks."
    admin     = person "Team admin"   "Invites and removes members."
    google    = softwareSystem "Google / Microsoft OIDC" "External" "external"

    todo = softwareSystem "Teamly todo" {
      web  = container "Web"  "Vue 3"        "spa"
      api  = container "API"  ".NET 10"      "service" {
        domain      = component "Domain"         "Entities and rules"
        application = component "Application"    "Use-case handlers"
        infra       = component "Infrastructure" "EF Core, OIDC"
      }
      db   = container "Database" "PostgreSQL 17" "database"
    }

    member -> web "Uses"
    web    -> api "REST over TLS"
    api    -> db  "EF Core"
    api    -> google "OIDC, outbound only"
    application -> domain "depends on"
    infra       -> application "implements"
  }
}
```

`views.dsl` is authored, not generated: it names which diagrams to render, their layout and any filtering, so a team can add a view without touching the model and without that view being lost on the next generation.

### C4 levels map onto HLD and LLD exactly

| Level | Diagram | Appears in | Answers |
| --- | --- | --- | --- |
| 1 Context | The system in its world: users, roles, external systems | HLD | Who uses this and what does it talk to |
| 2 Container | Deployables: web, api, database, queue, jobs | HLD | What are the moving parts and how do they communicate |
| 3 Component | Modules inside a container, with layer boundaries | LLD | How is each part built internally |
| 4 Code | Only where it earns its place, generated from real types | LLD | What are the actual classes and their relations |

Level 4 is generated only for elements flagged `detail: code` in `views.dsl`, because a class diagram of an entire system is noise. The default is the two or three aggregates with the most complex behaviour.

### Diagrams beyond C4

| Diagram | Generated from | Appears in |
| --- | --- | --- |
| Sequence, one per flow | `product/design/flows.md` plus the requirements in each flow | HLD |
| Trust boundary overlay | Data classifications and the boundaries in `architecture.md` | HLD, security report |
| Entity relationship | `product/entities.md` | LLD, data model |
| State machine, one per entity with a lifecycle | Requirement state transitions | LLD |
| Dependency graph | Verified package list with licences and ages | LLD appendix |

### Rendering

SVG for Markdown and HTML, PNG for Word and PDF, both committed so a document renders offline and in five years. Diagrams use the brand palette and typeface from `brand.yml`, with a contrast check: a diagram whose label text fails WCAG AA against its fill is re-rendered with a darker derived shade rather than shipped unreadable.

## 4. Templates

**Most teams never need a template.** VibeKit has a built-in structure for all five documents, and `brand.yml` supplies the letterhead. That combination is what makes a document look like yours; the section order rarely is.

A template is an override, for the case where your organisation mandates a particular document structure. Take over one document with `vibekit docs --scaffold-templates hld`, which writes a single `docs/templates/hld.md` for you to edit. From then on that file wins for that document, and the other four keep using the built-in structure. There is no requirement to have all five, and no `templates/` folder at all until you ask for one.

```markdown
# {{project.name}} — High Level Design
{{brand.classification_banner}}

Version {{doc.version}} · {{doc.date}} · generated from commit {{doc.commit}}
Prepared by {{company.name}} · {{company.department}}

## 1. Purpose and scope
{{product.context}}

## 2. System context
{{diagram.c4.context}}
{{narrative.context}}

## 3. Containers
{{diagram.c4.container}}
{{table.containers}}

## 4. Key flows
{{diagram.sequence.*}}

## 5. Quality attributes
{{table.quality}}

## 6. Security and trust boundaries
{{diagram.trust_boundaries}}
{{table.data_classification}}

## 7. Decisions
{{table.adr_index}}

## 8. Assumptions and open questions
{{table.assumptions}}
{{table.open_asks}}
```

### Placeholder reference

| Group | Placeholders |
| --- | --- |
| `project` | `.name` `.description` `.repo` `.version` |
| `company` | `.name` `.tagline` `.department` `.footer` — from `brand.yml` |
| `brand` | `.logo` `.logo_mono` `.classification_banner` `.colour.*` |
| `doc` | `.version` `.date` `.commit` `.tag` `.author` `.kind` |
| `product` | `.context` `.glossary` `.out_of_scope` |
| `diagram` | `.c4.context` `.c4.container` `.c4.component.<name>` `.c4.code.<name>` `.sequence.<flow>` `.sequence.*` `.erd` `.state.<entity>` `.trust_boundaries` `.deployment` |
| `table` | `.containers` `.components` `.entities` `.fields.<entity>` `.access_matrix` `.quality` `.invariants` `.dependencies` `.data_classification` `.adr_index` `.assumptions` `.open_asks` `.endpoints` `.requirements` `.changelog` |
| `narrative` | `.context` `.containers` `.components` `.flows` `.security` — generated prose, two to four paragraphs each |
| `authored` | `.<anything>` — a section VibeKit never fills; whatever you wrote there is preserved verbatim on every regeneration |

`{{diagram.sequence.*}}` expands to every flow in order. `{{table.fields.Booking}}` narrows a table to one entity. An unrecognised placeholder is left in place untouched and reported by name, so a template with a section VibeKit cannot fill still produces a usable document with an obvious gap rather than silently dropping it.

### Rules

- `vibekit docs --scaffold-templates <doc>` writes one template, for the document you name. It refuses to overwrite an existing one unless `--force` is given, and then only after showing a diff.
- A document with no template in `docs/templates/` uses the built-in structure. Deleting a template reverts that document to the built-in structure, which is the easy way out if a customisation stops being worth maintaining.
- `vibekit check` reports placeholders that stopped resolving after a spec change — for example `{{table.access_matrix}}` in a project that never defined one.
- Sections marked `{{authored.*}}` survive every regeneration. This is how an executive summary or a commercial section written by a person lives inside a generated document.
- A template may include another: `{{include:common-footer.md}}`.
- Templates are versioned with the repo, so a document regenerated at an old tag uses the template as it was then.

### Output formats

Markdown by default. `--docx` applies `styles.dotx` when present, mapping heading levels, table styles and the page footer. `--pdf` applies `brand.yml` directly. `--html` produces a single self-contained file with the diagrams inlined as SVG. Diagrams are embedded as SVG in Markdown and HTML, PNG in Word and PDF.

### Sharing a house style

`vibekit tools config templates <git url>` points a project at a shared repository holding `brand.yml`, `assets/` and any template overrides, cloned read-only at generation time. One place to change the company letterhead; every project follows. A project overrides a single file by committing its own copy, which takes precedence and is reported so the divergence is visible.

## 5. No template? Build one from a website

Most teams do not have a document template, and the ones that do often cannot find the file. This removes the excuse.

```bash
vibekit docs --brand https://acme.co.za
  fetched acme.co.za · 1 logo, 4 colours, 2 typefaces, 1 wordmark
  → docs/brand.yml
  → docs/assets/logo.svg  logo-mono.svg  favicon.png
  preview: docs/brand-preview.pdf
```

Two files and a preview, not a folder of templates. The built-in document structures pick the brand up immediately.

### What it extracts

| Asset | Where it looks | Fallback |
| --- | --- | --- |
| Logo | `<link rel=icon>`, `og:image`, an `<img>` or inline `<svg>` in the header, a file named logo or wordmark | A wordmark set in the brand typeface |
| Mono logo | A single-colour variant if one exists, otherwise flattened from the primary | Generated |
| Colours | CSS custom properties first (`--brand`, `--primary`), then the computed palette of header, buttons and links ranked by prominence | A neutral palette |
| Typefaces | `font-family` on headings and body, matched to a Google Font or a system stack | The house default |
| Company name, tagline | `og:site_name`, `<title>`, the footer | Asked |
| Legal footer | The footer: company number, registered address, classification wording | Left blank and flagged |

It writes `brand.yml`, downloads the assets, and renders a one-page `brand-preview.pdf` showing a cover, a heading, a table and a diagram in the extracted style — so you can judge it before committing. No templates are created: the built-in structures use the brand straight away.

```yaml
# docs/brand.yml · generated from acme.co.za on 2026-09-23 · edit freely
source: acme.co.za, fetched 2026-09-23
company:
  name: Acme Logistics
  tagline: Freight, simplified
  footer: Acme Logistics (Pty) Ltd · 2019/123456/07 · Durban, South Africa
logo:
  primary: assets/logo.svg
  mono: assets/logo-mono.svg
  favicon: assets/favicon.png
colour:
  brand: "#0B4F6C"
  accent: "#F4A300"
  text: "#14171C"
  text_on_brand: "#FFFFFF"
  note: brand colour darkened to #083D54 for body text (AA contrast)
type:
  heading: Poppins, system-ui, sans-serif
  body: Source Sans 3, system-ui, sans-serif
  mono: JetBrains Mono, monospace
document:
  classification_banner: "Confidential — Acme Logistics"
  page_size: A4
```

### Contrast is checked on the way in

A brand colour that fails WCAG AA as body text is kept for accents, and a darker derived shade is used for text. This is recorded in `brand.yml` as a note rather than done silently, so nobody is surprised that the document text is not exactly the brand hex. The same check applies to diagram labels.

### Rules

- **Only public pages, and only on request.** The fetch happens when you run the command with a URL. Nothing crawls on its own, `robots.txt` is respected, and one page plus its stylesheet is enough.
- **Assets are downloaded once and committed.** Templates reference local files, never a remote URL, so a document renders identically offline and in five years.
- **The logo belongs to its owner.** On first use VibeKit states that the logo and marks are the customer's property and that you are responsible for having permission. One line, not a dialog, and the provenance is recorded in `brand.yml`.
- **Everything is editable afterwards.** `brand.yml` and the templates are Authored. Change a colour, swap the logo, rewrite a section: VibeKit never touches them again.
- **A failed or partial extraction is reported, not guessed.** No logo found means the wordmark fallback and a line saying so, not a plausible-looking logo from somewhere else.

### Other sources

`--brand` also accepts a file: a PDF brand guide, a Figma tokens export, a Word document with the letterhead, or an image of a letterhead. The same extraction runs and produces the same `brand.yml`.

For your own company, run it once against your own site and commit `brand.yml` and `assets/` to a shared repository; `vibekit tools config templates <git url>` then points every new project at it, so the house style is a clone rather than a copy-paste. For client work, run it per client and the deliverables come out in their livery.

## 6. The five documents

### High Level Design

For an architect, a client, or a review board. Should be readable by a technical person who has never seen the code.

| Section | Contents | Source |
| --- | --- | --- |
| Purpose and scope | What the system is, who uses it, what is explicitly out of scope | `product/context.md` |
| System context | C4 level 1 diagram plus narrative | Model |
| Containers | C4 level 2 diagram, a table of each deployable with its technology and responsibility | Model, `map.md` |
| Key flows | One sequence diagram per flow | `design/flows.md`, requirements |
| Quality attributes | Performance, availability, retention, accessibility targets | `product/quality.md` |
| Security | Trust boundary diagram, data classification table | `architecture.md`, `entities.md` |
| Decisions | Index of ADRs with dates and status | `decisions/` |
| Assumptions and open questions | Every assumption with confidence and how many requirements rest on it; every open ask | `assumptions.md`, `workflow/asks/` |

That last section is unusual in an HLD and is the most valuable: it tells a reader exactly which parts of the design are standing on a guess.

### Low Level Design

For an engineer joining the project or picking up a module.

| Section | Contents | Source |
| --- | --- | --- |
| Component structure | C4 level 3 per container, with layer boundaries | Model, `map.md` |
| Design principles | Each principle with the test that enforces it | `architecture.md` design principles block |
| Code structure | C4 level 4 for the aggregates that warrant it | Model, real types |
| Data model | ERD plus field reference | `entities.md` |
| Access control | The role-by-entity matrix and the tests generated from it | `product/access.md` |
| Lifecycles | A state machine per entity that has one | Requirement transitions |
| Invariants | Each rule with its property test | `product/invariants.md` |
| Conventions | Error handling, logging, naming, where each kind of code goes | `standards/`, `map.md` |
| Dependencies | Every package with version, licence, last release | Verified dependency list |

### API reference

Generated from the contract tests and the OpenAPI document they pin, never from annotations that can drift. Every endpoint with method and path, auth requirement and required role, request and response shapes with field types, error shapes and status codes, and a worked example taken from the contract test itself — so the example is one that provably runs.

### Data model

The ERD, then per entity: every field with type, nullability, data classification, and validation rules; relations with cardinality; the retention and erasure rule for anything holding personal data; and the requirements that touch this entity, which is the reverse index nobody usually has.

### Runbook

Half generated, half authored, and the split is explicit in the file.

| Generated | Authored (never overwritten) |
| --- | --- |
| Health and readiness endpoints | Who to call, and when |
| Dependencies and what fails if each is down | Known failure modes and their symptoms |
| Environments, promotion rules, rollback command | Recovery steps that need judgement |
| Configuration and secret names | Maintenance windows, escalation policy |
| Recent incidents from reverts and rollbacks | Anything an operator learned the hard way |

VibeKit writes the structure and the facts it knows; the operator's knowledge lives under authored markers and survives every regeneration. A runbook that VibeKit could write entirely would not be worth reading.

## 7. Staying current

Two speeds, deliberately.

### The model updates continuously

Every requirement that reaches `done` updates `model.dsl` as part of the same commit. The model is never more than one merged requirement out of date, and the diff is visible in the pull request — a reviewer sees a new arrow between containers, or a new external system, and can question it before it lands. An architecture change that nobody noticed is an architecture change nobody agreed to.

### The documents regenerate at gates

Phase completion and every release run `vibekit docs`, producing a dated, commit-stamped set. The HLD someone was handed matches a tag and can be reproduced exactly:

```bash
vibekit docs --at v0.4.0
```

Generating on every merge would produce noise nobody reads and a diff on every pull request. Generating only on demand means it never happens. Gates are the right cadence because they are already the moment somebody looks.

### Drift checks

`vibekit drift` fails the build on any of these:

| Check | Why it matters |
| --- | --- |
| A container or component in the code that the model does not have | The documentation is already wrong |
| A relationship in the model with no code behind it | Usually a feature that was reverted, or a plan that changed |
| An entity in `entities.md` missing from the ERD | The data model document is incomplete |
| An endpoint in a contract test missing from the API reference | Somebody will integrate against a document that does not list it |
| A diagram older than the model it claims to render | Stale asset committed |
| A template placeholder that no longer resolves | A section will silently vanish from the next document |
| A generated document edited by hand | Reported as detached, with the date, so it is a decision rather than an accident |

### Diffing releases

```bash
vibekit docs --diff v0.3.0 v0.4.0
```

Reports what changed architecturally between two releases: containers added or removed, new external dependencies, entities and fields added, changed or dropped, endpoints added or altered, data classifications that moved, and decisions taken in that window. Output is prose plus the affected diagrams with changes highlighted.

This is what a client, an architecture review board or a security reviewer actually asks for, and it is the single hardest thing to produce by hand — which is why it is normally produced badly or not at all.

## 8. Commands, settings and acceptance

### Commands

| Command | Does |
| --- | --- |
| `vibekit docs` | Regenerate every document from the current folder |
| `vibekit docs hld \| lld \| api \| data \| runbook` | One document only |
| `vibekit docs --at <tag\|sha>` | Regenerate as things were at that commit |
| `vibekit docs --diff <a> <b>` | What changed architecturally between two points |
| `vibekit docs --brand <url\|file>` | Write `brand.yml`, the assets and a preview |
| `vibekit docs --scaffold-templates <doc>` | Take over one document's structure |
| `vibekit docs --model` | Regenerate `model.dsl` and the diagrams only |
| `vibekit docs --docx \| --pdf \| --html` | Output format; Markdown is the default |
| `vibekit drift` | Includes every documentation check in §7 |

### Settings in `profile.md`

| Setting | Default | Meaning |
| --- | --- | --- |
| `docs.enabled` | `true` | Turn the whole feature off |
| `docs.dir` | `docs/` | Where output lives |
| `docs.adr` | `true` | Generate ADRs from decision memories |
| `docs.formats` | `[md]` | Formats produced at gates |
| `docs.code_diagrams` | `auto` | Which elements get C4 level 4; `auto` picks the most complex aggregates |
| `docs.on` | `[phase, release]` | When documents regenerate |
| `docs.templates_repo` | none | Shared template repository |

### Acceptance

The feature passes when, on a real project:

1. A person who has never seen the code can read the HLD and correctly describe what the system does, what it talks to, and where personal data lives.
2. An engineer can read the LLD and correctly say where a new use-case handler goes, without asking anyone.
3. Every diagram matches the code, verified by `vibekit drift` passing on a repo whose model was generated three phases earlier.
4. `vibekit docs --at <old tag>` reproduces a document byte-identically to the one generated at that tag.
5. `--diff` between two releases lists every architectural change and misses none, checked by hand against the merge history.
6. A brand extracted from a website produces a document a client would accept without editing.
7. Regenerating after an unrelated requirement changes nothing in the documents — no churn, no reordered tables, no reshuffled diagram layouts. Deterministic output is what makes the diff useful.

Point 7 is the one most likely to fail in practice and the one worth testing first: diagram layout engines are not naturally deterministic, and a document that reshuffles itself on every run produces diffs nobody will read.

### Build order

1. **The model and the two C4 diagrams that matter.** `model.dsl` from `map.md`, `entities.md` and the architecture record; render context and container. This alone is worth more than the rest combined.
2. **Drift checks on the model.** Without these the model rots like any other document and the feature is pointless.
3. **HLD from the built-in structure**, with the placeholder system behind it.
4. **Brand extraction**, because it is the difference between a feature people try and one they use — and it is two files, so it is cheap.
5. **LLD, ERD and API reference.**
6. **`--at` and `--diff`.**
7. **Runbook, Word and PDF output, template overrides, shared brand repositories.**

A deliberate note on sequencing: steps 1 and 2 are the product. Everything after is presentation. A beautifully branded document generated from a model nobody checks is the same failure this feature exists to prevent, wearing a nicer jacket.
